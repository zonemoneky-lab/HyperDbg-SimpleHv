## Hook 5: MmQueryVirtualMemory (Protect -> PAGE_NOACCESS)

User request: add a hook for `MmQueryVirtualMemory`; when the queried address is
inside the protected module region, make the returned `Protect` = `NA`
(PAGE_NOACCESS). `MmQueryVirtualMemory` is NOT exported; locate it by signature
scan. User warned: scanning the `SizeOfImage` region will NEVER find it.

### Prototype (from user's NtQueryVirtualMemory decompile)
```c
NtQueryVirtualMemory(Handle, Base, Class, Info, InfoLen, RetLen)
    -> MmQueryVirtualMemory(Handle, Base, Class, Info, InfoLen, RetLen, 2)
```
7 params; 7th is a constant `2` (meaning unknown -> pass through unchanged).

### Signature (47 bytes, 13 wildcards)
```
4C 8B DC 53 56 57 41 54 41 55 41 56 41 57 48 81 EC ?? ?? ?? ??
48 8B 05 ?? ?? ?? ?? 48 33 C4 48 89 84 24 ?? ?? ?? ??
4C 89 4C 24 ?? 4D 63 F0
```
= prologue: `mov r11,rsp; push rbx/rsi/rdi/r12/r13/r14/r15; sub rsp,imm32;
mov rax,[rip+?]; xor rax,rsp; mov [rsp+?],rax; mov [rsp+?],r9; movsxd r14,eax`.

### The scan-range pitfall (user emphasized)
`SystemModuleInformation`'s `ImageSize` is too small on some builds (observed
~3.5MB), so scanning `[base, base+ImageSize)` never finds it. Fix: parse the
kernel PE header at the kernel base and use the **PE's real `SizeOfImage`**
(`NT+0x50`) as the scan range. Implemented in `MmQuery_GetImageSize()` with raw
offsets (no ntimage.h): `e_lfanew@DOS+0x3C`, `NumberOfSections@NT+0x06`,
`SizeOfOptionalHeader@NT+0x14`, `SizeOfImage@NT+0x50`,
section hdr@`NT+0x18+SizeOfOptionalHeader` (40 bytes each;
`VirtualSize@+0x08`, `VirtualAddress@+0x0C`). Logs the section table.

## FIX: the 47-byte signature was for the WRONG build (0 matches)

Runtime log: scan of `[kernelBase, +0x1450000)` (module-info ImageSize == PE
SizeOfImage here, so the scan range was fine) reported `signature not found`.

Offline analysis of `C:\Windows\System32\ntoskrnl.exe` (Python PE parser) proved:
- The original 47-byte sig (tail `4C 89 4C 24 ?? 4D 63 F0`) has **0 matches**
  anywhere in the image. Only the first 17 bytes (the shared prologue
  `4C 8B DC 53 56 57 41 54 41 55 41 56 41 57 48 81 EC`) matched, at 39 sites.
- The user's CORRECTED 45-byte sig (tail `49 8B F1 4D 63 E8`) matches **exactly
  once**, at RVA `0x9D9280` (IDA `0x1409D9280`), in the `PAGE` section.
  => runtime VA = kernelBase + 0x9D9280.

Lesson: a code signature must be generated from the SAME kernel it will run on;
a different build's prologue tail differs. Updated `test.c`
`MMQUERY_SIGNATURE_LEN` 47->45 and both `g_MmQuery_Signature` /
`g_MmQuery_Mask` arrays to the corrected 45-byte pattern (12 wildcards), plus a
hint in the failure log to regenerate the sig from this kernel's IDA.

### Offline technique that worked (reusable)
`C:\Windows\System32\ntoskrnl.exe` is the exact running image (section table
matched the runtime log byte-for-byte). Parse it in Python: DOS `e_lfanew@0x3C`,
sections at `NT+0x18+SizeOfOptionalHeader`, each 40 bytes
(`VirtualSize@+0x08`, `VirtualAddress@+0x0C`, `RawPtr@+0x14`, `RawSize@+0x10`);
map RVA<->file offset; then brute-force the wildcarded signature. Fast, no
kernel debugger needed. Export dir RVA/size @ `NT+0x18+0x70` / `+0x74`.

### Finding: NtQueryVirtualMemory is NOT reachable via a direct call
`ZwQueryVirtualMemory` IS exported (RVA 0x6ad530) but it is only a **syscall
stub** (`mov rax,rsp; cli; sub rsp,0x10; ...; mov eax,0x23; jmp
KiSystemServiceStart`). The real Nt body lives in `PAGE` and is reached via
`KiServiceTable`, not a relative call. So the MiCopy-style
"disassemble-the-export-to-find-the-internal-call" trick does NOT work for
syscalls. `KeServiceDescriptorTable` is also NOT exported on this build.
=> signature scan is the practical route here (which is what the user wanted).

## 已实现：TSC offset 补偿（反时序检测），分两档

用户说"行你可以试试"，于是把 HyperDbg 一直注释着的那套 TSC offsetting 落地了。

### 核心发现（这才是真正的 bug）
`VMCS_CTRL_TSC_OFFSET` 在 Vmx.c:853 已经写了 0，但**主控位
`USE_TSC_OFFSETTING` 没开**（Vmx.c 的 `CpuBasedVmExecControls` 里没有它），
硬件会**直接忽略**这个字段。常量在
`dependencies/ia32-doc/out/ia32.h:10967`
`IA32_VMX_PROCBASED_CTLS_USE_TSC_OFFSETTING_FLAG = 0x08`。
已加到主控位里。开着但 offset 为 0 时行为与之前完全一致，所以无副作用。

### 机制
guest 读 TSC = 宿主 TSC + VMCS TSC_OFFSET。每次 VM-exit 把"根模式耗时"
从 TSC_OFFSET 里减掉，guest 的 TSC 就等于没被打断过 —— 这样
`RDTSC -> CPUID -> RDTSC`（CPUID 无条件 VM-exit）测不出时间差。

### 两档模式（`header/transparency/VmxFootprints.h`）
- `TSC_OFFSET_COMPENSATION_OFF = 0`（默认，`g_TscOffsetCompensation` 是
  `.bss` 零初始化）
- `TSC_OFFSET_COMPENSATION_CPUID_ONLY = 1` —— **安全档**，只补偿
  CPUID/RDTSC/RDTSCP 引起的 VM-exit。CPUID 在正常负载里很少见，累计偏移极小，
  TSC 漂移和核间偏移可忽略，但足以干掉经典时序检测。
- `TSC_OFFSET_COMPENSATION_ALL_EXITS = 2` —— 激进档，补偿每一次 VM-exit
  （含自己 EPT hook 的 EPT violation）。最强，但 guest TSC 会持续落后于真实
  时间，且各核偏移独立累积 → 核间 TSC 漂移（Windows 有跨核 TSC 同步检查，
  QPC 也跟着 TSC 走）。仅适合短时测试。

这个分档是刻意设计：无条件补偿每一次 VM-exit 会让核间 TSC 漂移到可能触发
Windows 检查的程度，所以默认给安全档。

### 入口 TSC 的抓取（关键技巧，零栈布局改动）
`code/assembly/AsmVmexitHandler.asm`：在 **15 个 GPR 全部 push 完之后**、
`mov rcx, rsp` 之前插入
```
rdtsc / shl rdx,32 / or rax,rdx / mov rdx,rax
```
此时 guest 的 rax/rdx 已经存栈，clobber 它们是安全的；rdx 正好当第 2 个参数
（Windows x64 调用约定 RCX,RDX）。**RSP 全程没动**，所以 GUEST_REGS 指针和
整个栈帧布局、以及 AsmVmxoffHandler 的 `add rsp,0118h` 都不用改。
`VmxVmexitHandler(PGUEST_REGS, UINT64 TscAtVmexit)` 签名相应改了 3 处
（AsmVmexitHandler.asm / Vmexit.h:25 / Vmexit.c:23）。

### 新增文件/函数
- `Counters.c/.h`：`CounterApplyTscOffsetCompensation()`（带
  `TSC_OFFSET_MAX_STEP = 5000000` 钳位：Delta 异常就跳过，绝不写坏 TSC；
  并且 `ExitTsc <= TscAtVmexit` 时直接返回，保证 guest TSC 不回退）、
  `CounterResetTscOffset()`、`CounterGetTscOffset()`。
- **同时修了 `CounterEmulateRdtsc/Rdtscp`**：它们原来直接返回 `__rdtsc()`，
  在开了 RDTSC exiting + TSC offset 的情况下会跳变，现在加上
  `CounterGetTscOffset()`。
- `Vmexit.c`：handler 末尾按模式判断后补偿；`!VmxoffState.IsVmxoffExecuted`
  保护（VMXOFF 后 VMCS 就不是我们的了）。
- `Vmcall.h`：`VMCALL_RESET_TSC_OFFSET = 0x32`（0x31 之后下一个空号）；
  `Vmcall.c` 加 case → `CounterResetTscOffset`。
  路由已验证：`AsmVmxVmcall` 设 r10/r11/r12 = "HVFS"/"VMCALL"/"NOHYPERV"，
  `VmxHandleVmcallVmExit` 靠这个签名分流，新 VMCALL 会正常进
  `VmxVmcallHandler`。
- `DpcRoutines.c/.h` + `Broadcast.c/.h`：`BroadcastResetTscOffsetOnAllCores()`
  （关补偿时把各核 TSC_OFFSET 复位为 0）。
- `Export.c` + `HyperDbgVmmImports.h`：`VmFuncSetTscOffsetCompensation(UINT32 Mode)`。
  关闭时若 `g_GuestState[0].HasLaunched` 才广播，否则只警告（防止在没跑 VMX 时
  执行 VMCALL）。
- `DeviceIoctl.h/.c`：`IOCTL_SIMPLEHV_SET_TSC_OFFSET_COMPENSATION = 0x805`，

  `{Status, Mode, TotalCompensated, CompensationCount}`。
- `usermode/SimpleHvClient.h` + `main.cpp`：菜单第 6 项。

### 必须记住的取舍（已写进代码注释）
- 复位 TSC_OFFSET 会让 guest TSC **一次性向前跳变**累计偏移那么多 —— 这是刻意
  的，否则 guest TSC 会永久落后。刚开就关的话跳变可忽略。
- 统计量 `g_TscOffsetTotalCompensated` 是 `volatile UINT64` 的非原子 `+=`，
  多核会丢更新，只当信息量看，不要当精确值。
- 每次 VM-exit 都会多执行一条 `rdtsc`（~25 周期），即使补偿关闭也一样
  （汇编里不方便条件化，且用垃圾值有风险）。
- `VmFuncSetTscOffsetCompensation` **没有**自动挂在 transparent mode 上，
  唯一控制点是 IOCTL 第 6 项，行为可预测。

### 用户实测建议
用 `RDTSC -> CPUID -> RDTSC` 跑两轮对比：mode 1/2 下 delta 应该和裸机一致。
注意 ASM 序言/尾声那部分（约 150-300 周期）没有覆盖，只覆盖了 C handler
部分；对 EPT hook 这种 C 路径占大头的场景覆盖率高，对纯 CPUID 检测覆盖
约 70-85%。要做到 100% 覆盖得把 rdtsc 挪到 VM-exit 最开头，那就要动栈布局，
风险高，没做。
