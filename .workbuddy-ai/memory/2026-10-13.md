# 2026-10-13

## MiReadWriteVirtualMemory EPT Hook via Signature Scanning

Added Hook 3 to `test.c`: EPT inline hook on the unexported kernel function
`MiReadWriteVirtualMemory`, which is the internal routine that both
`NtReadVirtualMemory` and `NtWriteVirtualMemory` call for the actual
cross-process memory copy.

### Key implementation details

- **Signature scanning** replaces the previous E8-call-from-NtReadVirtualMemory
  approach. Pattern: `48 89 5C 24 ? 48 89 74 24 ? 4C 89 44 24 ? 48 89 54 24 ?
  57 41 54 41 55 41 56 41 57 48 83 EC` (32 bytes, 4 wildcards).
- **SizeOfImage workaround**: The reported `ImageSize` from
  `ZwQuerySystemInformation(SystemModuleInformation)` is only ~3.5MB on some
  builds. Solution: parse PE headers to find `.text` section and scan its
  `VirtualSize`. Fallback: scan 16MB from kernel base.
- **Kernel base obtained** via `ZwQuerySystemInformation(SystemModuleInformation)`
  resolved through `MmGetSystemRoutineAddress` (not directly declared in WDK
  kernel headers).
- **Hook handler** (`FakeMiReadWriteVirtualMemory`): calls original first, then
  if target process is in the protected list (cheatengine, x64dbg, ida, etc.),
  zeros the output buffer to prevent memory inspection.
- **Hook installation** follows the existing Hook 1/Hook 2 pattern using
  `ConfigureEptHook2` with trampoline output.
- `ResetTestHooksState` and `DeviceIoctl.c` updated to handle 3 hooks.

### Compile fixes (test.c 编译不了)

Root causes found by compiling test.c directly with cl.exe:

1. **Name collision**: the typedef `pMiReadWriteVirtualMemory` was moved above
   `InstallTestHooks`, colliding with the local `PVOID pMiReadWriteVirtualMemory`.
   Fixed by renaming the local to `pMiRWM`.
2. **PE header types unavailable**: `PIMAGE_NT_HEADERS` / `IMAGE_FIRST_SECTION` /
   `RtlImageNtHeader` are NOT declared unless `#include <ntimage.h>` is added
   (ZydisKernel.c does exactly that). Per user preference, avoided the header
   dependency entirely and parse the PE with **raw offsets**:
   - `e_lfanew` @ DOS+0x3C
   - NT sig @ NT+0x00, NumberOfSections @ NT+0x06, SizeOfOptionalHeader @ NT+0x14
   - AddressOfEntryPoint @ NT+0x28, SizeOfImage @ NT+0x50
   - section headers @ NT+0x18+SizeOfOptionalHeader, each 40 bytes:
     VirtualSize @ +0x08, VirtualAddress @ +0x0C
3. Replaced `ExAllocatePoolWithTag(...,'MVRW')` with the project's
   `PlatformMemAllocateZeroedNonPagedPool` / `PlatformMemFreePool`.
4. Removed a non-ASCII em-dash from a log string.

## Detailed logging added (MiRWM)

Goal: enough detail to debug resolution, without spamming.

- **`MiRWM_GetKernelBase`**: logs ZwQuerySystemInformation address, module-info
  buffer size, module count, and `Module[0]` path + base + reported ImageSize.
- **`ResolveMiReadWriteVirtualMemorySig`**: logs a `===== Resolving ... =====`
  banner; PE parse (`e_lfanew`, section count, optHdr size, SizeOfImage,
  EntryPoint); a per-section table (`section[i] 'name' VA VSize`); which pass
  matched; and a `===== RESOLVED =====` block with the final address, offset from
  kernel base, and a 16-byte hex dump of the matched bytes (helper
  `MiRWM_LogBytes`, no extra header deps). Failure paths log `FAILED: ...`.
- **Hook handler** (`FakeMiReadWriteVirtualMemory`): runtime log is **throttled**
  via `g_MiRWM_HookHitCount` / `MIRWM_HOOK_LOG_LIMIT` (=8) using
  `InterlockedIncrement` — prints `#N protected '<name>' intercepted ...` for the
  first 8 hits, then silent (buffer still zeroed). Non-protected accesses are
  never logged.
- **InstallTestHooks**: Hook 3 logs target + trampoline; final summary prints a
  per-hook `[OK]/[--]` status table instead of a blanket "all installed".
- `ResetTestHooksState` resets `g_MiRWM_HookHitCount`.

## MiRWM hook reworked to PID + module-address-range protection

Root cause of the user-reported **"param error"** (opening/reading any exe failed
once the hook was installed): `MiReadWriteVirtualMemory` is a **7-parameter**
function (a6 = PreviousMode, a7 = operation flag at `[rsp+0x38]`), but the
typedef declared only 6, so the 7th was never forwarded to the original. Fixed
by adding `ULONG_PTR Operation` as the 7th param to the typedef, forward decl,
and both call sites (passthrough + normal path).

The hook was then redesigned per user request to protect **only a module address
range inside one specific process**, instead of the old process-name blacklist:

- New config globals in `test.c`: `g_MiRWM_TargetPid`, `g_MiRWM_ProtectBase`,
  `g_MiRWM_ProtectSize`. `Size == 0` -> pure passthrough (zero system impact).
- New export `SetMiRWMProtectRange(pid, base, size)` (declared in `test.h`).
- `FakeMiReadWriteVirtualMemory`: passthrough when `Size==0`; otherwise
  `ObReferenceObjectByHandle` the target, match `PsGetProcessId` vs
  `g_MiRWM_TargetPid`, then zero only the **intersection** of the read range
  `[BaseAddress, +bytesTransferred)` with the protect range.
- Wiring through IOCTL:
  - `header/interface/DeviceIoctl.h`: `IOCTL_SIMPLEHV_SET_MIRWM_RANGE`
    (`0x803`) + `SIMPLEHV_SET_MIRWM_RANGE_REQUEST/RESPONSE` (all fields
    UINT32/UINT64 for layout parity).
  - `code/interface/DeviceIoctl.c`: `HandleIoctlSetMiRwmRange` (METHOD_BUFFERED,
    validates in/out lengths, reads request then writes response over the shared
    SystemBuffer) + dispatch case.
  - `usermode/SimpleHvClient.h`: same IOCTL + structs + `SetMiRwmRange()`.
  - `usermode/main.cpp`: menu option **4** "Set MiRWM Protect Range (PID +
    Module)" with `ReadUInt64` helper (base=0 -> auto 0x/decimal). PID 0 clears
    protection.

## "依旧能访问" root cause: Hook 3 install block was commented out

The runtime log showed `[--] 3. MiReadWriteVirtualMemory` in the status table.
Cause: the **entire Hook 3 install block in `InstallTestHooks` (test.c ~L545-586)
was commented out with `//`** (left over from the param-error debugging), so
`ConfigureEptHook2` for MiRWM never ran and `g_MiRWM_TestHookInstalled` stayed
FALSE. The SET_MIRWM_RANGE IOCTL worked fine — it just had no hook to configure.
Fix: re-enabled the block (resolution -> ConfigureEptHook2 -> trampoline checks).

### Robustness fixes to FakeMiReadWriteVirtualMemory

Web research (HyperCE deepwiki; CVE-2021-31956 writeup) shows the prototype
differs by build:
- older Win10: **6 params**, 6th = `ACCESS_MASK DesiredAccess`; `PreviousMode`
  is read from the current thread, NOT a parameter.
- newer builds: an extra stack parameter (7th).

So the typedef was changed to a **7-param superset** and the params renamed
`Arg6`/`Arg7` (positional passthrough only — a 7-param forward is safe whether
the real function takes 6 or 7):
- Do **not** treat Arg6 as PreviousMode. Mode now comes from
  `ExGetPreviousMode()` (stored in local `prevMode`, used for both the
  ObReferenceObjectByHandle guard and the ProbeForWrite guard). This was a
  latent bug: if Arg6 is really DesiredAccess, `Arg6 == UserMode(1)` would
  almost never hold and protection would silently never trigger.
- `ObReferenceObjectByHandle` now uses **DesiredAccess = 0** (reference only,
  no access check) so a handle opened without PROCESS_VM_READ still yields the
  EPROCESS for the PID comparison.
