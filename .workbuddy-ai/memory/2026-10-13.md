# 2026-10-13

## MiReadWriteVirtualMemory EPT Hook via Signature Scanning

Added Hook 3 to `test.c`: EPT inline hook on the unexported kernel function
`MiReadWriteVirtualMemory`, which is the internal routine that both
`NtReadVirtualMemory` and `NtWriteVirtualMemory` call for the actual
cross-process memory copy.

### Key implementation details

- **Signature scanning** replaces the previous E8-call-from-NtReadVirtualMemory
  approach. Pattern: `48 89 5C 24 ? 48 89 74 24 ? 4C 89 44 24 ? 48 89 54 24 ?
  57 41 54 41 55 41 56 41 57 48 83 EC` (32 bytes, 4 wildcards).
- **SizeOfImage workaround**: The reported `ImageSize` from
  `ZwQuerySystemInformation(SystemModuleInformation)` is only ~3.5MB on some
  builds. Solution: parse PE headers to find `.text` section and scan its
  `VirtualSize`. Fallback: scan 16MB from kernel base.
- **Kernel base obtained** via `ZwQuerySystemInformation(SystemModuleInformation)`
  resolved through `MmGetSystemRoutineAddress` (not directly declared in WDK
  kernel headers).
- **Hook handler** (`FakeMiReadWriteVirtualMemory`): calls original first, then
  if target process is in the protected list (cheatengine, x64dbg, ida, etc.),
  zeros the output buffer to prevent memory inspection.
- **Hook installation** follows the existing Hook 1/Hook 2 pattern using
  `ConfigureEptHook2` with trampoline output.
- `ResetTestHooksState` and `DeviceIoctl.c` updated to handle 3 hooks.

### Compile fixes (test.c 编译不了)

Root causes found by compiling test.c directly with cl.exe:

1. **Name collision**: the typedef `pMiReadWriteVirtualMemory` was moved above
   `InstallTestHooks`, colliding with the local `PVOID pMiReadWriteVirtualMemory`.
   Fixed by renaming the local to `pMiRWM`.
2. **PE header types unavailable**: `PIMAGE_NT_HEADERS` / `IMAGE_FIRST_SECTION` /
   `RtlImageNtHeader` are NOT declared unless `#include <ntimage.h>` is added
   (ZydisKernel.c does exactly that). Per user preference, avoided the header
   dependency entirely and parse the PE with **raw offsets**:
   - `e_lfanew` @ DOS+0x3C
   - NT sig @ NT+0x00, NumberOfSections @ NT+0x06, SizeOfOptionalHeader @ NT+0x14
   - AddressOfEntryPoint @ NT+0x28, SizeOfImage @ NT+0x50
   - section headers @ NT+0x18+SizeOfOptionalHeader, each 40 bytes:
     VirtualSize @ +0x08, VirtualAddress @ +0x0C
3. Replaced `ExAllocatePoolWithTag(...,'MVRW')` with the project's
   `PlatformMemAllocateZeroedNonPagedPool` / `PlatformMemFreePool`.
4. Removed a non-ASCII em-dash from a log string.

## Detailed logging added (MiRWM)

Goal: enough detail to debug resolution, without spamming.

- **`MiRWM_GetKernelBase`**: logs ZwQuerySystemInformation address, module-info
  buffer size, module count, and `Module[0]` path + base + reported ImageSize.
- **`ResolveMiReadWriteVirtualMemorySig`**: logs a `===== Resolving ... =====`
  banner; PE parse (`e_lfanew`, section count, optHdr size, SizeOfImage,
  EntryPoint); a per-section table (`section[i] 'name' VA VSize`); which pass
  matched; and a `===== RESOLVED =====` block with the final address, offset from
  kernel base, and a 16-byte hex dump of the matched bytes (helper
  `MiRWM_LogBytes`, no extra header deps). Failure paths log `FAILED: ...`.
- **Hook handler** (`FakeMiReadWriteVirtualMemory`): runtime log is **throttled**
  via `g_MiRWM_HookHitCount` / `MIRWM_HOOK_LOG_LIMIT` (=8) using
  `InterlockedIncrement` — prints `#N protected '<name>' intercepted ...` for the
  first 8 hits, then silent (buffer still zeroed). Non-protected accesses are
  never logged.
- **InstallTestHooks**: Hook 3 logs target + trampoline; final summary prints a
  per-hook `[OK]/[--]` status table instead of a blanket "all installed".
- `ResetTestHooksState` resets `g_MiRWM_HookHitCount`.

## MiRWM hook reworked to PID + module-address-range protection

Root cause of the user-reported **"param error"** (opening/reading any exe failed
once the hook was installed): `MiReadWriteVirtualMemory` is a **7-parameter**
function (a6 = PreviousMode, a7 = operation flag at `[rsp+0x38]`), but the
typedef declared only 6, so the 7th was never forwarded to the original. Fixed
by adding `ULONG_PTR Operation` as the 7th param to the typedef, forward decl,
and both call sites (passthrough + normal path).

The hook was then redesigned per user request to protect **only a module address
range inside one specific process**, instead of the old process-name blacklist:

- New config globals in `test.c`: `g_MiRWM_TargetPid`, `g_MiRWM_ProtectBase`,
  `g_MiRWM_ProtectSize`. `Size == 0` -> pure passthrough (zero system impact).
- New export `SetMiRWMProtectRange(pid, base, size)` (declared in `test.h`).
- `FakeMiReadWriteVirtualMemory`: passthrough when `Size==0`; otherwise
  `ObReferenceObjectByHandle` the target, match `PsGetProcessId` vs
  `g_MiRWM_TargetPid`, then zero only the **intersection** of the read range
  `[BaseAddress, +bytesTransferred)` with the protect range.
- Wiring through IOCTL:
  - `header/interface/DeviceIoctl.h`: `IOCTL_SIMPLEHV_SET_MIRWM_RANGE`
    (`0x803`) + `SIMPLEHV_SET_MIRWM_RANGE_REQUEST/RESPONSE` (all fields
    UINT32/UINT64 for layout parity).
  - `code/interface/DeviceIoctl.c`: `HandleIoctlSetMiRwmRange` (METHOD_BUFFERED,
    validates in/out lengths, reads request then writes response over the shared
    SystemBuffer) + dispatch case.
  - `usermode/SimpleHvClient.h`: same IOCTL + structs + `SetMiRwmRange()`.
  - `usermode/main.cpp`: menu option **4** "Set MiRWM Protect Range (PID +
    Module)" with `ReadUInt64` helper (base=0 -> auto 0x/decimal). PID 0 clears
    protection.

### Convention reinforced
Output/log **strings stay ASCII**; Chinese only in comments. `main.cpp` console
output was kept English to avoid C4566 / mojibake under a non-UTF-8 console.

`cl -Zs` syntax-check passes (exit 0) for `test.c`, `code/interface/DeviceIoctl.c`

The runtime log showed `[--] 3. MiReadWriteVirtualMemory` in the status table.
Cause: the **entire Hook 3 install block in `InstallTestHooks` (test.c ~L545-586)

### Robustness fixes to FakeMiReadWriteVirtualMemory

Web research (HyperCE deepwiki; CVE-2021-31956 writeup) shows the prototype
differs by build:
- older Win10: **6 params**, 6th = `ACCESS_MASK DesiredAccess`; `PreviousMode`
  is read from the current thread, NOT a parameter.
- newer builds: an extra stack parameter (7th).

So the typedef was changed to a **7-param superset** and the params renamed
`Arg6`/`Arg7` (positional passthrough only — a 7-param forward is safe whether
the real function takes 6 or 7):
- Do **not** treat Arg6 as PreviousMode. Mode now comes from
  `ExGetPreviousMode()` (stored in local `prevMode`, used for both the
  ObReferenceObjectByHandle guard and the ProbeForWrite guard). This was a
  latent bug: if Arg6 is really DesiredAccess, `Arg6 == UserMode(1)` would
  almost never hold and protection would silently never trigger.
- `ObReferenceObjectByHandle` now uses **DesiredAccess = 0** (reference only,
  no access check) so a handle opened without PROCESS_VM_READ still yields the
  EPROCESS for the PID comparison.

   passthrough; if opening exes no longer errors, the param fix is confirmed.
2. Menu 4 to set PID+base+size, then attempt a cross-process read of that range
   -> should come back zeroed.

## Added Hook 4: MmCopyMemory

New EPT hook on the **exported** kernel routine `MmCopyMemory` (resolved via
`MmGetSystemRoutineAddress`, unlike MiRWM which needs signature scanning).

### Design (incorporates the three points the user called out)
- **Range overlap, not just start address**: helper `MmCopy_RangesOverlap()`
  does a half-open interval intersection `[addr,addr+len) ∩ [regionStart,+size)`
  with integer-overflow guards (overflow -> treat as overlapping, block).
- **VIRTUAL vs PHYSICAL are distinct** (`MM_COPY_MEMORY_VIRTUAL=0x2`,
  `MM_COPY_MEMORY_PHYSICAL=0x1` from ntddk.h):
  - VIRTUAL: use `SourceAddress.VirtualAddress` directly.
  - PHYSICAL: cannot compare a physical address to a virtual region; map it
    with `MmGetVirtualForPhysical()` first, then compare (mapping failure ->
    passthrough, to avoid false positives).
- **No PID inside a virtual address**: `SourceAddress.VirtualAddress` carries no
  process identity. Config has an optional `g_HideMemTargetPid` — when non-zero,
  only block if the **current address-space context** (`PsGetCurrentProcessId()`)
  matches; 0 = block any process.

### Files touched
- `test.c`: `pMmCopyMemory` typedef; `old_MmCopyMemory`, `g_MmCopyTestHookInstalled`;
  hide-region config `g_HideMemRegionStart/Size` + `g_HideMemTargetPid`;
  `MMCOPY_HOOK_LOG_LIMIT`(=8) throttle; `MmCopy_RangesOverlap()`; export
  `SetMmCopyHideRegion(pid,start,size)`; handler `MmCopyMemoryHook`; install as
  **Hook 4**; status table now lists 4 hooks.
- **Install-flow label chaining fixed**: each hook's "already installed" / "not
  found" path now `goto` the NEXT hook's label (`install_hook_3`, `install_hook_4`)
  instead of jumping straight to `hooks_installed`. Previously an
  already-installed Hook 2 would skip Hook 3 (and now Hook 4) entirely.
- Block status: `MMCOPY_BLOCK_STATUS` = `0xC0000018`
  (STATUS_CONFLICTING_ADDRESSES — the code from the user's reference; macro'd so
  it is easy to switch to STATUS_INVALID_ADDRESS 0xC0000141).
- `test.h`: declared `SetMmCopyHideRegion`.
- `header/interface/DeviceIoctl.h` + `code/interface/DeviceIoctl.c`:
  `IOCTL_SIMPLEHV_SET_MMCOPY_REGION` (0x804) + request/response structs +
  `HandleIoctlSetMmCopyRegion`; install response `HooksInstalled` now `4`.
- `usermode/SimpleHvClient.h`: IOCTL/structs + `SetMmCopyRegion()`.
- `usermode/main.cpp`: menu option **5** "Set MmCopyMemory Hide Region".

### Verified
`cl -Zs` passes (exit 0) for `test.c`, `DeviceIoctl.c`, `usermode/main.cpp`.
Only pre-existing warnings remain (SDK C4005, test.c C4142/C4047).

## Hook 3 retargeted: MiReadWriteVirtualMemory -> MiCopyVirtualMemory (no pattern scan)

User insight: the call chain is
`NtRead/NtWriteVirtualMemory -> MiReadWriteVirtualMemory -> MiCopyVirtualMemory`,
and `MmCopyVirtualMemory` is just an exported wrapper of `MiCopyVirtualMemory`.
So hooking `MiCopyVirtualMemory` once covers ALL of those paths. And because
`MmCopyVirtualMemory` is exported, its address is trivial to get — the internal
`MiCopyVirtualMemory` is the target of the relative call/jmp inside it. This
removes the IDA signature scan entirely.

### What changed in `test.c`
- **Deleted** the whole pattern-scanning machinery: `g_MiRWM_Signature`,
  `g_MiRWM_Mask`, `g_MiRWM_SigLen`, `MiRWM_FindPattern`, `MiRWM_GetKernelBase`,
  `MiRWM_LogBytes`, the PE-offset `#define`s, and
  `ResolveMiReadWriteVirtualMemorySig`.
- **Added** `ResolveMiCopyVirtualMemory()` + helper
  `MiCopy_FindRelativeCallTarget()`: `MmGetSystemRoutineAddress(L"MmCopyVirtualMemory")`,
  then **Zydis** (`ZydisDecoderInit` / `ZydisDecoderDecodeFull`, already available
  via `pch.h`) walks the prologue (first `MICOPY_DISASM_SCAN_LEN` = 0x60 bytes),
  logging every relative `call`/`jmp`, and returns the first target in kernel
  space (`>= 0xFFFF000000000000`, != self). Uses
  `operands[0].imm.is_relative` + `imm.value.s`.
- **Handler** renamed `FakeMiReadWriteVirtualMemory` -> `FakeMiCopyVirtualMemory`
  with the 7-param `MmCopyVirtualMemory` signature
  `(PEPROCESS SourceProcess, PVOID SourceAddress, PEPROCESS TargetProcess,
   PVOID TargetAddress, SIZE_T BufferSize, KPROCESSOR_MODE PreviousMode,
   PSIZE_T ReturnSize)`. No more `ObReferenceObjectByHandle` — we already have
  `PEPROCESS`, so the source PID is just `PsGetProcessId(SourceProcess)`.
  Overlap logic + zeroing the caller's `TargetAddress` buffer unchanged.
  Fixed the `ProbeForRead(ReturnSize)` path to only probe when
  `PreviousMode == UserMode` (a kernel pointer would otherwise fault and skip
  the zeroing).
- Typedef `pMiReadWriteVirtualMemory` -> `pMiCopyVirtualMemory`; global
  `old_MiReadWriteVirtualMemory` -> `old_MiCopyVirtualMemory`; local `pMiRWM` ->
  `pMiCopy`. Kept the `g_MiRWM_*` config names + `SetMiRWMProtectRange` so the
  existing IOCTL / usermode protocol is unchanged (documented in comments).
- Status table line 3 now reads `MiCopyVirtualMemory`.

Hook 4 (`MmCopyMemory`) and all the IOCTL/usermode plumbing are unchanged.

### Verified
`cl -Zs` passes (exit 0) for the refactored `test.c`.

## MiCopyVirtualMemory: added WRITE interception (was read-only)

User pointed out the handler only covered reads. `MiCopyVirtualMemory` is a
generic copy; the direction is decided by the **target process**:
- read : `Source` = process being read, `Target` = caller
- write: `Source` = caller,              `Target` = process being written

So `FakeMiCopyVirtualMemory` now does BOTH directions:

1. **Write (blocked)**: if `TargetProcess` PID == `g_MiRWM_TargetPid` and
   `RangesOverlap(TargetAddress, BufferSize, protBase, protSize)` -> return
   `MICOPY_WRITE_BLOCK_STATUS` (= `0xC0000022` STATUS_ACCESS_DENIED) and set
   `*ReturnSize = 0`. This happens **before** calling the original — a write
   can't be undone once it lands, so it must be refused up front (unlike the
   read path which zeroes the caller's output buffer afterwards).
2. **Read (zeroed)**: unchanged — call original, then zero the intersection in
   the caller's `TargetAddress` buffer when `SourceProcess` PID matches.

Also:
- Renamed the shared helper `MmCopy_RangesOverlap` -> `RangesOverlap` (now used
  by both Hook 3 and Hook 4).
- New throttle counter `g_MiRWM_WriteBlockCount` (reset in `ResetTestHooksState`).
- **Self-copies pass through (both directions)**: `SourceProcess == TargetProcess`
  (= the protected process touching its own memory) is NOT intercepted and NOT
  zeroed — otherwise the protected process's own data would be corrupted.
  Guard added to both the write-block condition and the read-zero check.
  (This supersedes an earlier "block self-copies too" decision; the user wants
  the process's own memory operations allowed.)

## BUG: reads never intercepted — ProbeForRead on a KERNEL ReturnSize

Symptom from the runtime log: all 4 hooks installed, WRITE blocking worked
(`[MiCopy Hook] #1 BLOCKED WRITE ...`), but **no read interception at all**.

Root cause: in the read path the handler did
`if (PreviousMode == UserMode) ProbeForRead(ReturnSize, sizeof(SIZE_T), ...)`.
But in the `NtReadVirtualMemory -> MiReadWriteVirtualMemory -> MiCopyVirtualMemory`
chain, `ReturnSize` is **MiReadWriteVirtualMemory's own local variable address**
(kernel stack) while `PreviousMode` is still `UserMode`. `ProbeForRead` on a
kernel address raises `STATUS_ACCESS_VIOLATION` immediately; the `__except` set
`haveByteCount = FALSE` and the zeroing was silently skipped. The write path was
unaffected because it decides to block *before* calling the original and never
needs `ReturnSize` to make the decision.

Fix (read path):
- Never `ProbeForRead`/`ProbeForWrite` `ReturnSize` — it may be a kernel pointer.
  Read/write it directly inside `__try/__except`; the handler falls back to
  `bytesTransferred = BufferSize` (correct for `STATUS_SUCCESS`).
- Dropped `ProbeForWrite` on the destination buffer too (the address was already
  validated by the original call; `__try` catches faults).
- Added a guard `TargetProcess == PsGetCurrentProcess()` before touching
  `TargetAddress`, so we only write when the destination is in the current
  address space (otherwise `RtlZeroMemory` would hit the wrong process's memory).

Diagnostic added: the read path now logs **either** `... READ [...] hits protect
range -> zeroed N bytes` **or** `... READ [...] reached hook but NOT zeroed
(haveBytes=.. dstInCurProc=..)` (throttled to `MIRWM_HOOK_LOG_LIMIT`). If neither
line ever appears for a read of the protected process, the read is not going
through `MiCopyVirtualMemory` on that build and a different function must be
hooked.

### Verified
`cl -Zs` passes (exit 0) after the fix.

## Hook 4 (MmCopyMemory) review — user confirmed Hook 3 r/w works

Read/write interception on Hook 3 confirmed working by the user. Review of
`MmCopyMemoryHook` found:

1. **Real low-level bug (fixed)**: `*NumberOfBytesTransferred = 0` was written
   with no `__try` guard — an invalid caller pointer would BSOD. Now wrapped in
   `__try/__except` (same treatment as `FakeMiCopyVirtualMemory`'s `*ReturnSize`).
2. **`NTAPI` added** to `MmCopyMemoryHook` for consistency with the reference
   (`__stdcall`) and `FakeMiCopyVirtualMemory` (no-op on x64, clarity only).
3. **Physical-address blind spot made visible**: when
   `MmGetVirtualForPhysical()` returns NULL the call passes through. Added a
   throttled log (`g_MmCopy_PhysMissCount`, reset in `ResetTestHooksState`) so
   physical-source attempts that can't be resolved are at least visible.

Known limitation (documented, not "fixed"): the PHYSICAL branch maps the source
physical address to a VA and compares that against the (virtual) hide region.
A physical read of the page backing the hidden region maps to the system's
physical-memory VA, not the original virtual address, so it will normally not
match — physical-address reads can therefore bypass the block. Properly closing
this needs translating the hidden VA range to PFNs (page-table walk). Also
`Flags ==` equality is used (matches the documented "exactly one flag" contract);
a caller passing both bits falls through to passthrough.

### Verified
`cl -Zs` passes (exit 0) after the Hook 4 review.

### Decision: PHYSICAL bypass will NOT be closed
User explicitly declined implementing the page-table walk (hidden VA range -> PFN)
to close the documented PHYSICAL-source bypass in `MmCopyMemoryHook`. Leave the
PHYSICAL branch as-is (map via `MmGetVirtualForPhysical`, passthrough on failure).
Do NOT re-propose this. The bypass remains a documented limitation only.
